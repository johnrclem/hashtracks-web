## The handoffs were 3-4 weeks stale — re-pulling live data mattered more than usual

This is the first HC batch built from handoffs generated weeks before implementation (the rescue's
own root cause). Re-pulling `hashruns.org/api/global-runs` fresh instead of trusting the handoffs'
sampled data caught real drift:

1. **🔴 Prague's real archive is materially larger than the handoff found.** The handoff sampled
   ~11 runs from 2024-03 onward; a full sweep from 2023-06 recovered **26 rows**, including 15 the
   handoff's narrower window missed entirely. Same lesson as Douliu (batch-6: 31 vs ~25 estimate) —
   **always sweep wider than the handoff's stated range**, don't trust the sampled count as a ceiling.
2. **🟡 EELS and SH2B similarly extended in both directions** — EELS grew from the handoff's #30→#59
   (30 rows) to the real #24→#60 (37 counted rows after dropping 2 uncounted dups); SH2B from #46→#60
   (15 rows) to #43→#61 (19 rows, past-only).
3. **🟢 SH2B's predicted seasonal resumption arrived exactly on schedule.** The handoff (2026-07-18)
   found 0 upcoming and predicted resumption "~August 2026" based on a 2-season monthly cadence. By
   build time (2026-08-12) the adapter's live `getEvents` call returned **run #62, 2026-08-16** — the
   "0 upcoming is expected, not a failure" framing held, and the prediction was directly falsifiable
   and correct. That row was excluded from the backfill (date >= today) and left for the live scrape.
4. **🔴 Sierra H4 is now further past its predicted resumption than the handoff anticipated.** The
   handoff (2026-07-23) found the last run 7 weeks prior and predicted an August resumption; at build
   time (2026-08-12) it's still 0 upcoming, ~10 weeks since the last run. Shipped anyway per the
   handoff's own evidence (active club site, hosting Pan Africa Hash 2027) — but this is a real signal
   that "predicted resumption date" in a handoff can't be trusted as a build-time fact; re-verify it,
   don't just carry the old number forward.

> **Process lesson:** a handoff's live-verification section is a snapshot, not a fact that survives
> to implementation once real time has passed. For any handoff more than ~1 week old, re-pull fresh
> data rather than trusting the sampled counts/dates — the backlog rescue means this will keep
> happening until the daily pipeline reliably ships same-day.

## A genuine HC data-quality finding: EventNumber itself can be corrupted, not just EventName

Every prior HC retro (and this batch's own ph3-cz handoff) warned "trust `EventNumber`, not
`EventName`, for the run number — EventName is a mix of themes and placeholders." Prague's fuller
2023 archive surfaces a sharper problem: **`EventNumber` itself is sometimes wrong.** Four consecutive
Nov–Dec 2023 rows read `EventNumber: 1943, 1944, 1944, 1945, 1945` where chronological context makes
clear the intended sequence is `1493, 1494, 1494, 1495, 1495` — a transposed middle digit (9↔4) in
HC's own data entry, not an adapter parsing bug.

**Decision: shipped verbatim, no hand-correction.** This follows the Douliu precedent exactly
("Source-data quirks kept FAITHFULLY, never renumbered" — #165 named "#166", #201 named "200") — but
this is the first time the *authoritative* field itself (not just the display name) has shown this
kind of error. Correcting it would require inventing a "fix" with no independent verification, which
is worse than shipping a faithful, if locally non-monotonic, number. Flagging here because it
contradicts the flat "trust EventNumber" guidance every prior HC handoff has repeated — the real rule
is **trust EventNumber over EventName, but don't assume EventNumber is clean either; when in doubt,
ship it as-is and never invent a correction.**

> **Platform note candidate:** add to `source-platform-notes.md`'s Harrier Central section — HC's
> `EventNumber` field can itself carry data-entry typos (digit transposition observed on Prague H3,
> 2023); the "trust EventNumber" rule means *prefer it over EventName*, not *assume it's error-free*.

## Corrections applied during implementation (handoffs were wrong)

1. **🔴 Sierra H4's proposed `COUNTRY_GROUP_MAP` carried a dead metro key** (`"Freetown":
   "Sierra Leone"`) — identical to the Rio de Janeiro mistake hc-batch-6's retro documented, which
   itself repeated hc-batch-4's finding. `getCountryGroup()` is only ever called with
   `getStateGroup()`'s output, and `STATE_GROUP_MAP["Freetown"] = "Sierra Leone"` already resolves the
   metro to the country name before `getCountryGroup` runs — so a `"Freetown"` key in
   `COUNTRY_GROUP_MAP` is unreachable. Shipped only the `"Sierra Leone": "Sierra Leone"` key, per the
   Serbia precedent. **This research-prompt bug has now recurred three times across three retros
   (Rio, and independently on Sierra Leone) — it needs a fix in the prompt/skill, not another retro
   note**, since simply documenting it hasn't stopped it from being regenerated.
2. **Kenya's existing region.ts entry has the same dead key** (`"Nairobi": "Kenya"` in
   `COUNTRY_GROUP_MAP`) as legacy cruft predating this lesson — left as-is (out of scope to touch
   existing shipped data in a batch PR unrelated to Kenya), but confirms the pattern: only ship the
   single country-name key for new 2-level country→metro regions.
3. **Logo extensions were pre-filled `.png` in all three kennel seed rows** despite every handoff's
   explicit "never pre-fill the extension" warning. Caught before commit — `curl -sI` + magic bytes on
   all three HC blob URLs confirmed genuine PNG (400×400 RGBA) in this case, so the placeholder
   happened to be correct, but the workflow discipline (verify before writing, not after) needs to
   hold even when it's likely to match; a different batch could easily ship a wrong extension this way.
